## 记录口径

- 沿用既有契约测试的 12 类及各类数量，构造适合真实 API 执行的输入；多轮步骤属于同一个场景，场景数、用户运行数、A2A 任务数分别统计。
- 类内采用不同日常、学术和业务场景，具体输入与预先定义的标准见 NATURAL100_DESIGN.md；6份长文本是完整原创材料，没有重复句或占位字符凑长度。
- 顺序来自 A2A TaskStore 的真实创建/更新时间。表格按开始时间排序；时间区间重叠表示并发，不表示后一项必须等前一项结束。
- Worker 内部工具调用按持久 journal 的顺序列出；journal 没有单次工具精确时间戳，因此不编造工具耗时。输出只保留摘要。
- Host 负责接收、鉴权、轮次落库、上下文装配、调度和最终提交；状态/摘要/长期事实抽取是 Host 后台任务，不计作额外 A2A 子 Agent。
- 恢复类别是真实 pause/continue；没有在用户正在使用的服务上强制杀进程。进程崩溃能力另由恢复单测验证。
- 每轮评测期限为360秒。到期即记录timeout并请求停止；之后即使得到迟到答复也不追认通过，迟到产物仅供问题分析。
- 每类选择有代表性的自然表达与任务链，包含失败示例；所有失败保留在下一节和机器可读汇总中，不能从代表例推断整类全部通过。
- 答案中的 `/api/evidence/…` 是测试实例内的引用地址，公开仓库不提供该服务的私有证据数据库；工具返回只展示状态、数量、来源地址等摘要。

# 客户工单看板交接说明

## 1. 系统概况与职责边界
- **看板定位**：看板每小时从工单平台拉取新增记录，展示待处理数量、超时工单和负责人分布。看板是展示层，**不是底层计费系统**，不处理账务。
- **发票咨询处理**：休假期间若客户询问发票金额，应转给财务接口人处理；不得因看板含客户名称而代为解释账务。
- **当前运行状态**：主流程运行正常。上周三有一批历史工单补录，导致当天新增数量明显升高，这不是新投诉涌入。
- **数据导出要求**：重新导出数据时必须保留补录标记，不得将补录记录混入正常新增趋势。

## 2. 日常运维与故障处理 SOP
### 2.1 每日失败同步检查（固定动作）
- **检查时间**：每天上午 10 点前查看昨天的失败同步列表。
- **常见原因**：多数失败源于附件暂时不可访问，稍后重试通常恢复，无需立即升级。
- **升级路径**：同一工单连续三次失败后，将**工单号**和**错误时间**发到内部支持群。
- **隐私红线**：禁止在支持群粘贴客户附件内容（尤其含地址、电话的截图），仅上报工单号与错误时间。

### 2.2 告警与恢复验证
- **重复告警**：告警邮件可能在短时间内重复发送，收到重复告警不代表故障扩大，先确认是否同一事件。
- **恢复记录**：确认服务恢复后，记录恢复时间和受影响区间；不能仅凭邮件停止就推断数据已补齐。
- **补数核验**：补数是否完成需对照源平台记录数量核验，必要时抽查若干工单的创建与更新时间。

### 2.3 周一例会准备
- **内容结构**：准备上周新增、结案、未解决问题三个部分。
- **数据口径**：所有数字从同一份导出表计算，避免看板实时值与固定周期数据混用。
- **案例脱敏**：异常案例只展示脱敏后的工单描述，不附客户原始联系方式。

### 3.1 未结案问题
1. **负责人字段偶尔为空**：源平台允许未分派工单，属正常业务状态，不是数据丢失，无需当故障处理。

### 3.2 导出超时临时处理
- **操作步骤**：先缩小导出日期范围，降低单次数据量；提交后等任务列表出现结果再下载，不要反复点击。
- **升级条件**：超过两天（业务处理约定）仍无法完成，升级给研发排查。
- **概念区分**：“两天”是业务响应约定，不是后台任务应持续运行的时长；技术超时与业务响应时间是两个独立概念。

### 3.3 生产配置变更与权限
- **变更流程**：生产配置修改必须先提交变更记录，由值班负责人审核后执行。
- **权限规范**：权限申请走现有审批流程，不得绕过；交接说明不含账号密码，不允许共用登录。

## 多会话场景的角色与条件

跨会话记忆类：第一轮本人陈述，第二轮同用户新会话召回，第三轮关闭长期记忆后再次开新会话。隔离类前五例：本人陈述→本人正向召回→另一用户询问；后五例：本人查询私有资料→另一用户查询→同用户切换到其他知识库查询。每个查询均使用自然问题，不把文档准确名称写入问题。

隔离类的综合失败不等同于数据泄漏：若本人正向召回失败或前置记忆没有形成，不能仅凭另一用户答不知道判定隔离已经验证。该类应结合每轮身份、记忆注入数量及回答判断。
