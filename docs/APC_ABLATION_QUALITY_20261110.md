# APC 真开关消融与端到端质量评测

日期：2026-11-10。结论：APC 对追加式 Worker 轨迹有明确的 Prefill 收益；本次
“稳定字段前置＋工具排序”候选没有稳定的额外收益，也没有达到默认启用的质量标准。
保留正式服务原配置，`PREFIX_CACHE_LAYOUT=false`。测试实例已停止。

## 1. 实际完成了什么

- 独立 vLLM 实例真正以 `--no-enable-prefix-caching` 和
  `--enable-prefix-caching` 分别启动。两个启动参数数组仅此一项不同。
  日志分别记录 `enable_prefix_caching=False/True`。
- 固定请求回放：APC 开、关各 180 次，共 **360 次**，每工况重复 3 次。
- 完整业务评测：4 组 × 9 个场景 × 每组 19 个用户轮次，共 **36 个主场景、76 轮**。
  实际经过 Host、A2A 业务角色、SQLite、记忆处理及真实私有检索工具。
- 项目隔离补测：4 组各 1 个正反对照场景、2 轮，共 **4 个补充场景、8 轮**。
  合计 **40 个场景实例、84 个完整用户轮次**，不是仅调用记忆模块。
- 保存全部请求、响应、工具轨迹、最终答案、失败状态、逐例复核理由和原始指标。
  没有覆盖失败记录，也没有挑选重跑后的最好结果。

| 组别 | 输入组织 | APC |
|---|---|---|
| A | 原布局 | 关闭 |

## 2. 固定条件和测量边界

使用 215 的两张 H100 80GB，同一 Qwen3.5 架构权重、BF16、TP=2、vLLM 0.23.0。
对外模型名称仍为 qwen3.8-27b。独立测试服务在 127.0.0.1:8010，正式 8000 服务
未重启或改配置。为同时容纳模型，四组统一使用 32768 上下文、0.40 显存预算；
max_num_seqs=16，max_num_batched_tokens=8192，Attention block size=784 Token。
这与正式服务的 131072/0.50 不同，所以不把测试延迟当作正式部署的绝对性能。

推理开关的固定请求回放先做 off、后做 on；各阶段内部工况以固定随机顺序排列。
完整任务按 A、C、D、B 顺序运行，每组用独立数据目录和账号，业务并行度固定为 1。
采集代理统一设置 temperature=0、seed=42，完整任务保留各角色原输出上限。
这是相同语义场景的独立执行；账号、会话、来源和证据 UUID 不同，完整任务不是
逐 Token 相同的模型输入，工具选择和生成长度也可能变化。

两份模型驻留同两张 GPU，未锁定 GPU 时钟，因此不把小延迟差异认定为稳定提升。
固定回放的请求采样前运行数均为 0；本测试实例的指标一致性另有逐请求验证。
没有完成并发 2/4/8 的吞吐扫描，不作高并发结论。

### 固定请求回放

沿用首轮真实 Worker checkpoint 的 2/4/8 轮轨迹、8 个真实任务输入及仅改变
current_request 的受控样本。工具 Schema 经当前 MCP 适配器重建，未宣称是原始
线上绑定工具集合的逐字节抓包。四组使用同一生成脚本和同一 checkpoint 文件。

输出固定为 1 Token，顺序回放，共享组内 cache_salt；此处 salt 只隔离不同试验的
缓存，**APC 开关由引擎启动参数实际控制**。每组第一条建缓存请求保留在原始记录，
汇总后续请求时排除它。8 轮工况因此是 3 次重复、每次 7 条后续请求，共 21 条。

使用服务端 `/tokenize` 和 Prometheus TTFT/Prefill 指标。单 Token 可能被工具解析器
隐藏，客户端 TTFT 的 null 保持原样，不用请求总耗时代替。

一致性检查结果：

- 开／关两边 180 个输入 Token 长度逐项相等，所有输出长度为 1。
- 每个模型请求的服务端 TTFT count 均恰好增加 1。
- 关闭 APC：prefix queries 与 hits 总增量均为 0。
- 开启 APC：查询增量 548751 Token，命中增量 206976 Token（包含全部负载及首条请求）。
- 启动参数数组只有 prefix-caching 布尔开关不同。

## 3. 真开关性能结果

8 轮 Worker 工况，后续请求：

| 组别 | 服务端 TTFT 均值 | Prefill 均值 | 缓存 Token 比例 | 请求耗时中位数 |
|---|---:|---:|---:|---:|
| A 原布局、APC 关 | 305.4 ms | 275.7 ms | 0% | 321.0 ms |
| B 原布局、APC 开 | 149.8 ms | 124.1 ms | 84.04% | 147.1 ms |
| C 候选布局、APC 关 | 296.8 ms | 270.5 ms | 0% | 306.4 ms |
| D 候选布局、APC 开 | 130.6 ms | 102.7 ms | 84.02% | 132.7 ms |

**B 对 A：TTFT 下降 51.0%，Prefill 下降 55.0%。** 这是现有 vLLM APC 的贡献，
不能归为本次输入重排新增的收益。D 对 C 的 TTFT 下降 56.0%。

D 相对 B 的汇总均值低约 19 ms，但看三次重复的 TTFT 均值：

| 重复 | B 原布局＋APC | D 候选＋APC |
|---|---:|---:|
| 1 | 138.9 ms | 142.6 ms |
| 2 | 200.7 ms | 137.8 ms |
| 3 | 109.9 ms | 111.3 ms |

候选在三次中有两次更慢，且实际命中比例没有增加。因此不认定它有稳定的额外
性能收益，不用一次均值差异宣传“再加速 13%”。

其他负载也并非都受益：原布局 2/4 轮工具轨迹的 TTFT 分别从 253.9/266.3 ms
降到 119.0/134.9 ms；真实任务组原布局从 225.9 到 232.7 ms；受控当前请求变化
组从 222.0 到 248.9 ms，且实际命中为 0。APC 的收益依赖可复用轨迹，不能只报
最有利的 Worker 数据。

## 5. 优化思路及取舍

本次改动集中在**输入组织**，缓存计算由 vLLM 提供：

1. **识别重复输入**：先区分角色提示词、工具定义、历史、当前请求；用实际模板的
   Token 前缀和真实缓存指标验证，不能用相同字符数替代命中。
2. **提高连续前缀的稳定性**：候选把语言、固定能力说明、摘要/记忆/近期历史等
   顶层字段前置，将本轮变化留后；Worker 工具按完整名称排序，减少发现顺序扰动。
   它是两项组合候选，本轮未把字段顺序与工具排序进一步分别消融。
3. **保留语义与失效机制**：不删除字段，不把已变更记忆冻结在旧快照中；来源标识、
   版本、权限 manifest 和记忆回执全部保留。更新、删除和换用户/项目时正常重建输入。
4. **用四组实验归因**：B−A/D−C 检查引擎缓存作用；D−B 看候选增量；C−A 排查输入
   重排自身对生成路径和质量的影响。最终还要查看真实任务产物，而不仅是 TTFT。

本轮最有效的是 Worker 已有的**追加式工具轨迹**。它能复用先前输入，公共前缀
随轨迹增长。相比之下，受控请求中候选只将公共前缀从 2158 增到 2208 Token，
增加 50 Token；在 784 Token 缓存块及混合注意力状态约束下，没有形成新增实际命中。
块边界只是解释的一部分，不能仅用整除关系完全解释零命中。

混合模型要求不同层类型的缓存命中同时满足；APC 主要减少重复 Prefill，
不自动缩短工具等待和长输出 Decode。
参考：[APC 官方说明](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)、
[混合缓存机制](https://docs.vllm.ai/en/stable/design/hybrid_kv_cache_manager/)。

**决策：不发布本候选为默认布局。** 已有 APC 的重复轨迹收益成立；候选没有可靠
新增命中，并产生了质量问题。本次完成的是评测和候选筛选，不宣称整体 Agent
已实现无退化加速。后续若继续优化，应从真实轨迹的首次变化位置、稳定历史块及
混合模型可复用状态边界入手，再做组件独立消融；避免通过多加无用 Token 来凑块。
